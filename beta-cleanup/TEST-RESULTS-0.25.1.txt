What the new regression tests actually exercised
- Remove a polished backing track using its settings dialog; save; Undo;
  save again; reload. Both lanes keep their valid processed audio and hashes.
- Rename a track; Undo; change a POLISH effect; save. Cleanup does not Redo.
  An explicit Redo still works. An omitted history direction is harmless.
- Overlapping save requests restore the latest title with valid audio references.
- A deliberately injected QuotaExceededError produces a visible backup/retry
  banner. The last successful save remains intact. Retry can save successfully.
- Stereo -> mono -> stereo through the real track settings controls, on the
  same bound lane. The input channel count changes, originals and breath edits
  survive, readiness is correct, and processed export is allowed. Reload retains
  the selected input mode.
- A real legacy-render seam differs from the current renderer. Modern backup
  contains explicit input WAV, and reopening preserves the input exactly and the
  final on the documented 16-bit grid.
- Deleting one processed audio record from browser storage preserves its editable
  settings, warns visibly, stays flagged after another save, and can rebuild the
  final from its saved input.
- The owner's supplied My song ZIP opens as a selected lead take with 55 notes,
  enters POLISH through the normal button, retains its A minor key, accepts a
  new edit, saves/reloads, and reopens from a new backup as a usable polished lane.
  Test edits were made only in isolated browser sessions; the original ZIP is intact.
- Show vocal reaches the selected waveform while transport remains visible.
  The POLISH waveform shortcut opens/focuses its editor. No horizontal overflow
  at the four tested widths; phone shortcuts meet 44-pixel touch targets.

Large-song storage investigation
The original temporary-browser capacity run failed after processing all three
four-minute lanes, playing them together and exporting their stems/mix. The same
failure remained after the application fixes, at about 320 MB reported usage,
while the browser advertised about 2.47 GB quota.

An independent IndexedDB-only probe, without application code, then wrote 64 MiB
records. The temporary browser profile accepted eight records (~512 MiB) and
rejected the ninth with QuotaExceededError, while still reporting over 2 GiB quota.
A normal disk-backed browser profile accepted all fourteen records (896 MiB).
This isolates a temporary-profile storage ceiling in this test environment; it
is not evidence that every user's device has the same limit. The app's visible
backup/retry response is retained for real storage failures.

Full-song verification in normal disk-backed profiles
The same four-minute lead + two four-minute backing lanes + ten 18-second phrase
fixes (15 minutes of source recordings) successfully:
- processed all three lanes with separate manual breath edits;
- played the three processed lanes together;
- exported three processed stems and the processed vocal mix;
- saved to browser storage (~486 MiB), then reloaded with identical final hashes
  and the same per-lane edits;
- created a 218.3 MiB modern project and a 650.9 MiB compatibility project;
- reopened both projects in separate fresh disk-backed browser profiles, with
  every lane valid, the same edits, and matching final audio (modern: 16-bit grid;
  compatibility: exact float hashes).
The main run produced no browser console errors.

The complete capacity suite finished with 22 passed, 0 failed. A nine-minute
lane was refused in 0.1 ms while the existing editor, its audio and its screen
remained unchanged. The UI explained the refusal and marked that lane blocked.
